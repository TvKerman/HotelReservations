# ADR-003: Алгоритм выбора номера и защита от конкурентного overbooking

## Контекст

При создании бронирования без явного указания номера система должна выбрать номер из доступных в отеле. Требования:

1. **Равномерность распределения.** Предпочтение отдаётся менее загруженным номерам. Это снижает вероятность, что часть номеров простаивает, а другие используются постоянно.
2. **Отсутствие конкурентного overbooking.** При одновременных запросах на один и тот же номер не более одного запроса должно завершиться созданием активной брони.
3. **Детерминированность.** Одинаковые входные данные при отсутствии конкурирующих операций должны приводить к одинаковому выбору.

## Решение

### Алгоритм выбора

1. `booking-service` обращается в `hotel-service` по эндпойнту `GET /hotels/{hotelId}/rooms/available`.
2. `hotel-service` возвращает все номера отеля, отсортированные:
   ```sql
   ORDER BY times_booked ASC, id ASC
   ```
3. `booking-service` последовательно проверяет номера в полученном порядке, отбрасывая те, у которых есть пересечение дат с активными бронями (запрос `countOverlappingActive`).
4. Первый подходящий номер выбирается для бронирования.

Сортировка по `times_booked ASC` обеспечивает статистическую равномерность: каждый новый выбор приходится на наименее загруженный номер. При равенстве `times_booked` сортировка по `id ASC` обеспечивает детерминированность.

Значение `times_booked` инкрементируется при успешном подтверждении брони и декрементируется при её отмене (best effort, с использованием `@Retry`).

### Защита от overbooking

Ключевой механизм — **декларативное ограничение на уровне PostgreSQL**:

```sql
ALTER TABLE bookings ADD CONSTRAINT no_overlapping_active_bookings
    EXCLUDE USING gist (room_id WITH =, period WITH &&)
    WHERE (status <> 'CANCELLED');
```

где `period` — генерируемая колонка типа `DATERANGE`:

```sql
period DATERANGE GENERATED ALWAYS AS (daterange(check_in, check_out, '[)')) STORED
```

Ограничение проверяет пересечение по диапазону дат с учётом `room_id`. Брони в статусе `CANCELLED` исключены из проверки — они не блокируют новые бронирования того же номера на те же даты.

### Обработка конкурентных сбоев

При параллельных вставках PostgreSQL может вернуть одну из двух ошибок:
- `23P01` — нарушение `EXCLUDE` constraint (штатный сценарий, бронь отклоняется с `409 Conflict`).
- `40P01` — deadlock (редкий сценарий при определённом порядке блокировок внутри индекса).

`booking-service` обрабатывает оба случая как конфликт (`409`), что семантически корректно: клиент видит, что запрошенные даты недоступны, а не внутреннюю ошибку сервиса.

## Рассмотренные альтернативы

### Pessimistic locking (`SELECT ... FOR UPDATE`)

Перед вставкой — блокировка строки номера через `SELECT ... FOR UPDATE`, затем проверка пересечений и вставка.

Отклонено:
- Создаёт конкуренцию на уровне строк даже для непересекающихся по датам броней одного номера (что неоптимально).
- Требует явного управления блокировкой в коде и порядка захвата (риск deadlock).
- `EXCLUDE` — декларативный механизм; проверка и ограничение выполняются СУБД как единое целое.

### Optimistic locking (`@Version` на `Room`)

Использование поля `version` для обнаружения конфликта при обновлении счётчика.

Отклонено как **основной механизм** (сохранён как вспомогательный):
- Защищает от параллельных обновлений одной строки, но не от «параллельной вставки двух броней с пересекающимися датами» — обе вставки в `bookings` могут пройти, так как они не изменяют одну и ту же строку `rooms`.
- Требует ручной обработки `OptimisticLockException` и повторов.

`@Version` в сущности `Room` сохранён для защиты от гонки при обновлении `times_booked`.

### Проверка пересечений только в коде (без ограничения в БД)

`SELECT count(*) WHERE room_id = ? AND overlap` перед `INSERT`.

Отклонено:
- Race condition: два потока одновременно выполняют `SELECT` и получают результат «свободно», после чего оба выполняют `INSERT`. Оба бронирования успешно создаются.
- Проверка в коде — необходимое, но не достаточное условие. В реализованном решении она сохранена как fast-path для пользовательского выбора, но финальная гарантия обеспечивается БД.

### Distributed lock (Redis)

Взятие распределённой блокировки на `room_id` перед операцией.

Отклонено:
- Требует дополнительной инфраструктуры.
- Сложность обработки отказа Redis (что делать при потере соединения во время удержания блокировки).
- `EXCLUDE` решает задачу без внешних зависимостей.

## Последствия

### Положительные

- Инвариант «не более одной активной брони на пересекающиеся даты» обеспечивается на уровне СУБД и не может быть нарушен приложением при любом уровне конкуренции. Подтверждено тестом `BookingIntegrationTest.Parallel`: 10 одновременных потоков на один номер → 1 `CONFIRMED`, 9 `409 Conflict`.
- Декларативность: ограничение описано в миграции, не требует поддержки в коде.
- Равномерность распределения: сортировка по `times_booked` обеспечивает выбор наименее загруженного номера без необходимости в статистических моделях.

### Отрицательные

- `EXCLUDE USING gist` — специфичная возможность PostgreSQL. Перенос на другую СУБД потребовал бы пересмотра подхода.
- Требуется расширение `btree_gist` (создаётся в миграции).
- Под высокой нагрузкой возможны deadlock (код `40P01`), требующие явной обработки в сервисе и преобразования в `409 Conflict`. Это осознанный компромисс: deadlock — редкое событие, а корректность инварианта важнее, чем полное отсутствие конфликтов блокировок.
- На экстремальных уровнях конкуренции возможно замедление вставок из-за проверки индекса.
