# ADR-001: Оркестрация распределённой транзакции через сагу с компенсацией

## Контекст

Операция бронирования затрагивает данные в двух сервисах:
- `booking-service` создаёт запись в таблице `bookings`;
- `hotel-service` инкрементирует счётчик `times_booked` у выбранного номера.

Требуется обеспечить согласованность: бронирование не должно оставаться в состоянии «подтверждено», если резервирование номера не удалось. Классический подход к распределённым транзакциям — two-phase commit (2PC) — не подходит по причинам, приведённым ниже.

## Решение

Применена orchestration-сага со следующей последовательностью шагов:

1. Создание записи бронирования в состоянии `PENDING`.
2. Вызов `POST /hotels/{hotelId}/rooms/{roomId}/increment-booked` в `hotel-service` через `HotelResilientClient`.
3. При успешном ответе — перевод бронирования в `CONFIRMED`.
4. При сбое downstream-вызова — перевод в `CANCELLED`.

Компенсирующее действие в случае неудачи шага 2 не требуется (инкремент не был выполнен). Компенсация предусмотрена только для случая отмены уже подтверждённой брони: вызывается `decrement-booked` (best effort).

### Защита downstream-вызова

`HotelResilientClient` оборачивает Feign-клиент Resilience4j:

| Механизм | Конфигурация |
|---|---|
| Retry | 3 попытки, экспоненциальная задержка (200ms × 2ⁿ), повтор только для retryable-исключений |
| CircuitBreaker | Sliding window 10, минимум 5 вызовов, порог сбоев 50%, пребывание в OPEN 5s, 3 пробных вызова в HALF_OPEN |
| Timeout | connect 2s, read 3s (уровень Feign) |

При сбое всех попыток `Retry` пробрасывает исключение, `CircuitBreaker` регистрирует отказ, `booking-service` переводит бронь в `CANCELLED` и возвращает клиенту `201 Created` с финальным статусом `CANCELLED`.

## Рассмотренные альтернативы

### Two-phase commit (XA)

PostgreSQL поддерживает подготовленные транзакции (`PREPARE TRANSACTION`). Однако:

- Требуется установка `max_prepared_transactions > 0` и настройка менеджера транзакций.
- Соединение занято между `prepare` и `commit` — что нарушает работу пула HikariCP и несовместимо с моделью «соединение на время запроса».
- Spring Cloud не предоставляет готовой обвязки для XA; интеграция требовала бы существенной ручной работы.

Для системы из пяти сервисов стоимость реализации и эксплуатации существенно превышает выгоду.

### Choreography через брокер сообщений

Альтернатива с асинхронной передачей событий (`BookingCreated`, `RoomReserved` и т.п.) через Kafka или RabbitMQ:

- Требует развёртывания и сопровождения брокера.
- Усложняет диагностику: распределённая цепочка событий менее прозрачна, чем явные вызовы в одном оркестраторе.
- Для учебного проекта с малым количеством сценариев выгода не оправдывает дополнительную инфраструктуру.

### Transactional outbox с гарантией доставки

Наиболее корректный для продуктивной системы вариант:

- Событие записывается в `outbox` в той же транзакции, что и изменение агрегата.
- Фоновый процесс читает `outbox` и публикует события в брокер.
- Гарантия at-least-once доставки и восстановление после сбоя.

Отклонено для данного проекта в силу сложности: требуется реализация планировщика, идемпотентности обработки событий и dead-letter queue.

### Общая база данных с одной транзакцией

Простейшее техническое решение — размещение `bookings` и `rooms` в одной БД, что позволяет использовать локальную транзакцию и `EXCLUDE` между таблицами.

Отклонено: нарушает принцип database-per-service и связанность сервисов через общую схему. Для микросервисной архитектуры это антипаттерн, снижающий независимость развёртывания и эволюции схемы.

## Последствия

### Положительные

- Явная последовательность шагов и единственная точка координации — упрощает тестирование и отладку.
- Компенсация явно выражена в коде (`CANCELLED` при сбое, `decrement-booked` при отмене).
- Resilience4j обеспечивает устойчивость при кратковременных сбоях downstream — подтверждено нагрузочным тестом: при остановке `hotel-service` 7 последовательных броней корректно переведены в `CANCELLED`; первый вызов потратил ~6.6s (три попытки Retry с таймаутами), последующие — ~27ms (сработал CircuitBreaker).

### Отрицательные

- Синхронный Feign-вызов блокирует поток обработки запроса. При недоступности `hotel-service` время отклика растёт до значений таймаута.
- `booking-service` — единая точка отказа оркестрации. При падении между созданием `PENDING` и финализацией статуса бронь остаётся в промежуточном состоянии.
- В продуктивной системе потребовался бы фоновый sweeper: периодический поиск броней в состоянии `PENDING` старше заданного таймаута с переводом в `CANCELLED` или повторным запуском саги. В текущей реализации такое поведение отсутствует — это осознанное упрощение.
