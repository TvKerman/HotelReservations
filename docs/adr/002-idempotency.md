# ADR-002: Идемпотентность операции создания бронирования

## Контекст

Клиент или промежуточные звенья (gateway, load balancer) могут повторно отправить запрос `POST /bookings` в случае сетевого сбоя или таймаута. Без явной обработки повторный запрос приводит к созданию дублирующей брони, что влечёт финансовые и операционные последствия.

Требуется обеспечить свойство идемпотентности: повторный запрос с теми же параметрами возвращает результат первого выполнения без побочных эффектов.

## Решение

Использован механизм на основе клиентского ключа идемпотентности.

### Механика

1. Клиент передаёт заголовок `Idempotency-Key: <строка>` (опционально).
2. В таблице `bookings` присутствует колонка `idempotency_key VARCHAR(64)`.
3. Создан **частичный уникальный индекс**:
   ```sql
   CREATE UNIQUE INDEX unique_idx_bookings_idempotency
       ON bookings(idempotency_key) WHERE idempotency_key IS NOT NULL;
   ```
4. В `BookingService.create()`:
   - При наличии ключа выполняется `findByIdempotencyKey()`. Если запись найдена — возвращается её DTO без выполнения побочных эффектов (без вызова `hotel-service`).
   - В противном случае — `INSERT` с указанным ключом.
   - При `DataIntegrityViolationException` (конкурентная вставка с тем же ключом) выполняется повторный `findByIdempotencyKey()` — один из параллельных запросов гарантированно получит существующую запись.

### Срок хранения ключа

Ключ хранится в той же строке, что и бронь, и живёт столько же, сколько бронь. Отдельный TTL не требуется.

## Рассмотренные альтернативы

### Хранение ключей в Redis с TTL

Стандартный подход в платёжных системах. Ключ помещается в Redis с TTL (обычно 24 часа), при повторном запросе — проверка наличия.

Отклонено:
- Требует дополнительной инфраструктуры (Redis).
- TTL должен превышать максимальное время жизни клиентского retry-окна; при этом для брони с длительным жизненным циклом (до 30+ дней) TTL 24 часа не защищает от повтора через день.
- Индекс в БД обеспечивает ту же семантику без дополнительных зависимостей.

### Естественный ключ: `user_id + hotel_id + room_id + check_in + check_out`

Уникальный составной индекс по перечисленным полям.

Отклонено:
- Легитимный повтор запроса с теми же параметрами через длительное время (например, пользователь снова хочет забронировать тот же номер на те же даты после отмены предыдущей брони) будет отклонён.
- Требует введения дополнительного параметра на клиенте для отмены дедупликации.

### Полный уникальный индекс на `idempotency_key`

`UNIQUE (idempotency_key)` без условия `WHERE`.

Отклонено:
- Существующие записи без ключа (`idempotency_key IS NULL`) формально допускаются уникальным индексом в PostgreSQL, но индекс включает эти строки, увеличивая размер и снижая эффективность.
- Частичный индекс явно выражает намерение: «уникальность гарантируется только для записей, где ключ явно задан».

## Последствия

### Положительные

- Клиент может безопасно повторять запрос при таймаутах и сетевых сбоях.
- Гарантия идемпотентности не теряется при перезапуске сервиса — она обеспечена уровнем БД.
- Частичный индекс не затрагивает существующие записи без ключа.
- Механизм не требует дополнительной инфраструктуры.

### Отрицательные

- Использование частичного индекса — специфичная возможность PostgreSQL, затрудняющая перенос на другие СУБД.
- Клиент обязан генерировать и передавать `Idempotency-Key` — это дополнительный контракт на стороне API.
- При отсутствии заголовка идемпотентность не гарантируется. Сервис не отклоняет такие запросы, полагая, что клиент осознанно не передал ключ.
