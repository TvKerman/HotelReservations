# ADR-006: Агрегация Swagger UI через API Gateway

## Контекст

Микросервисная архитектура предполагает наличие нескольких независимых сервисов (`auth`, `hotel`, `booking`), каждый из которых имеет свой собственный набор REST-эндпойнтов. Для удобства интеграции и тестирования требуется документация API (OpenAPI/Swagger).

Оставлять Swagger UI на каждом отдельном порту (`8081/swagger-ui.html`, `8082/swagger-ui.html` и т.д.) неудобно для клиентов и разработчиков. Также при прямом обращении к сервисам теряется сквозная маршрутизация, реализованная в API Gateway, что может приводить к ошибкам при тестировании защищённых эндпойнтов.

## Решение

Реализована **агрегация Swagger UI на уровне API Gateway**.

1. В `gateway-service` добавлена зависимость `springdoc-openapi-starter-webflux-ui`.
2. В `application.yaml` Gateway настроены специальные маршруты для загрузки спецификаций (`/api/auth/v3/api-docs`, `/api/hotels/v3/api-docs`, `/api/bookings/v3/api-docs`) с фильтром `StripPrefix=2`, который отсекает префикс `/api/*` перед отправкой запроса в сам сервис.
3. В конфигурации `springdoc.swagger-ui.urls` перечислены пути к этим спецификациям, что формирует выпадающий список сервисов в едином UI.
4. В `common/OpenApiConfig` явно задан базовый URL сервера (`/api`), чтобы Swagger UI корректно склеивал пути и отправлял запросы через Gateway, не дублируя префикс.

## Рассмотренные альтернативы

| Вариант | Почему отвергнут |
|---|---|
| **Swagger на каждом сервисе отдельно** | Плохой Developer Experience (DX). Разработчику пришлось бы переключаться между тремя разными вкладками и портами, а также самостоятельно конфигурировать базовые URL для запросов. |
| **Использование внешних инструментов (Redoc, Stoplight)** | Избыточно для данного проекта. SpringDoc нативно интегрируется со Spring Boot и WebFlux без необходимости поднимать дополнительные сервисы. |
| **Статическая генерация спецификаций** | Требует ручной работы при каждом изменении кода. Динамическая генерация через SpringDoc всегда актуальна. |

## Последствия

### Положительные

- **Единая точка входа:** вся документация доступна по одному адресу `http://localhost:8080/swagger-ui.html`.
- **Корректное тестирование:** кнопка "Try it out" отправляет запросы через Gateway, что полностью повторяет реальные сценарии клиента (включая работу JWT-фильтров и маршрутизацию).
- **Удобство для ментора/ревьюера:** проверка API занимает минимум времени.

### Отрицательные

- **Усложнение конфигурации Gateway:** требуется дублирование маршрутов (отдельно для API и отдельно для Swagger-спецификаций) и настройка `StripPrefix`.
- **Особенности безопасности:** пути `/swagger-ui/**` и `/v3/api-docs/**` должны быть добавлены в `permitAll` во всех `SecurityConfig` (как в Gateway, так и в самих сервисах), иначе UI будет отдавать `401 Unauthorized`.
