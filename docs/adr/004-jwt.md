# ADR-004: Аутентификация и авторизация на основе JWT

## Контекст

Требуется реализовать единую аутентификацию для всех сервисов при сохранении их независимости. Пользователь проходит аутентификацию один раз, после чего получает токен, действительный для всех защищённых операций во всех сервисах.

Дополнительное требование — каждый сервис должен самостоятельно отклонять невалидные и просроченные токены, не полагаясь исключительно на корректность проверки в API Gateway.

## Решение

### Формат токена

- Алгоритм подписи: **HS256** (симметричный, HMAC-SHA256).
- Секретный ключ: 32+ байта, передаётся через переменную окружения `JWT_SECRET`, общую для всех сервисов.
- Claims: `sub` (email), `uid` (id пользователя), `role` (`USER` / `ADMIN`), `iat`, `exp` (1 час), `iss` (`"auth-service"`).

### Аутентификация

`auth-service` реализует регистрацию и вход:
- Пароли хешируются BCrypt (cost 10) при регистрации.
- При входе — сверка `BCryptPasswordEncoder.matches()`.
- При успехе — генерация JWT через `NimbusJwtEncoder`.

`auth-service` не выполняет роль Resource Server. Он выпускает токены, но не валидирует их. Это семантически корректно: сервис аутентификации не должен требовать уже выданного токена для выдачи нового.

### Валидация

Каждый прикладной сервис (`hotel-service`, `booking-service`) и `gateway-service` реализуют роль **Resource Server**:

```java
@Bean
JwtDecoder jwtDecoder(@Value("${app.security.jwt.secret}") String secret) {
    var key = new SecretKeySpec(secret.getBytes(StandardCharsets.UTF_8), "HmacSHA256");
    return NimbusJwtDecoder.withSecretKey(key).macAlgorithm(MacAlgorithm.HS256).build();
}

@Bean
JwtAuthenticationConverter jwtAuthenticationConverter() {
    var converter = new JwtAuthenticationConverter();
    converter.setJwtGrantedAuthoritiesConverter(jwt -> {
        String role = jwt.getClaimAsString("role");
        return (role == null || role.isBlank()) ? List.of()
            : List.of(new SimpleGrantedAuthority("ROLE_" + role));
    });
    return converter;
}
```

Методная безопасность реализована через `@EnableMethodSecurity` и `@PreAuthorize("hasRole('ADMIN')")` на изменяющих эндпойнтах.

Gateway использует реактивную версию (`ReactiveJwtDecoder`, `ReactiveJwtAuthenticationConverterAdapter`), так как работает на WebFlux. Валидация на gateway — defense-in-depth, а не единственная линия защиты.

## Рассмотренные альтернативы

### RS256 (асимметричная подпись)

`auth-service` подписывает приватным ключом, остальные сервисы валидируют публичным.

Отклонено для данной задачи:
- Требуется эндпойнт JWKS для публикации ключей и их ротации.
- Усложняется конфигурация: вместо одной переменной окружения — менеджмент ключей.
- Для учебного проекта симметричный HS256 даёт эквивалентный уровень безопасности при существенно меньшей сложности.

Для продуктивной системы, где `auth-service` администрируется отдельной командой, RS256 был бы предпочтительнее.

### Валидация только на Gateway

Gateway проверяет JWT, downstream-сервисы доверяют проверке.

Отклонено:
- Нарушает defense-in-depth. При компрометации gateway или ошибке в маршрутизации защита полностью отсутствует.
- Сервисы становятся зависимыми от gateway — их нельзя использовать или тестировать автономно.
- Не соответствует практикам микросервисной безопасности: каждый сервис должен самостоятельно контролировать доступ к своим ресурсам.

### Opaque token с introspection

Токен — случайная строка, сервисы выполняют запрос к `auth-service` для проверки.

Отклонено:
- Дополнительный round-trip к `auth-service` на каждый защищённый запрос — существенное замедление.
- `auth-service` становится критической точкой отказа для всех операций.
- JWT с самодостаточными claims устраняет необходимость в централизованной проверке.

### Использование внешнего провайдера (Keycloak, Auth0)

Готовый OAuth2/OIDC-сервер.

Отклонено для данного проекта:
- Дополнительная инфраструктура и операционная сложность.
- Собственная реализация `auth-service` демонстрирует понимание протоколов JWT и Spring Security.
- Для продуктивной системы внешний провайдер был бы предпочтителен.

## Последствия

### Положительные

- Все сервисы валидируют токен самостоятельно — compromise gateway не открывает доступ к данным.
- Сервисы независимы: `hotel-service` можно запустить и тестировать без `gateway` и `auth`.
- Роль содержится в claim — не требуется дополнительный запрос за правами.
- 401/403 возвращаются в едином формате `ErrorDTO` через `JsonSecurityErrorHandler` (реализация `AuthenticationEntryPoint` и `AccessDeniedHandler`).

### Отрицательные

- Симметричный секрет известен всем сервисам — компрометация любого из них компрометирует всю систему. В продуктивной системе использовался бы RS256 с приватным ключом, доступным только `auth-service`.
- Отсутствует механизм отзыва токена (revocation). Выход из системы — удаление токена на клиенте; токен остаётся валидным до истечения `exp`. Для продуктивной системы потребовался бы blacklist или короткий TTL в сочетании с refresh token.
- Секрет передаётся через переменную окружения — ротация требует перезапуска всех сервисов.
- Время жизни токена фиксировано (1 час) и не настраивается per-user.
